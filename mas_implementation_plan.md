# План технической реализации: MAS/MAD-команда как плагины DeepSeek Harness

Этот документ — прямое продолжение `mas_audit_questions.md`, `mas_audit_answers.md`, `mas_deepened_analysis.md` и кода в `mas_toolkit/`. Здесь фиксируется, ЧТО и В КАКОМ ПОРЯДКЕ строится, а не заново обосновываются архитектурные решения — обоснования уже даны в предыдущих файлах со ссылками на источники.

---

## 0. Стратегическое решение, определяющее весь план

Продукт реализуется **не как отдельное приложение**, а как **набор Cordis-плагинов к DeepSeek Harness**, которые:

1. добавляют бэкенд-логику (оркестратор, планировщик, критик, event log и т.д. — расширение модулей из `mas_toolkit/`) в плагинную систему Harness наравне с нативными плагинами (`llm`, `session`, `tools`);
2. добавляют собственные панели в **родной Web UI** Harness (`dsh web`) — по тому же механизму, каким сторонние плагины `dsh-dashboard` уже добавляют целый кастомный дашборд, а `dsh-usage-chart` — встроенную визуализацию расхода токенов прямо под полем ввода.

Следствие: мы не пишем чат-рендерер, обработку markdown, настройки, механизм хранения учётных данных — всё это уже есть в Harness и уже работает локально (`~/.dsh`, сервис слушает только `127.0.0.1`). Это резко сокращает объём работы при ограниченном бюджете — именно поэтому этот пункт стоит первым, он определяет масштаб всего остального.

## 1. Слои системы

*(см. диаграмму выше)* Локальный процесс Harness — единственная граница доверия по умолчанию. Внутри — два региона: (а) Web UI с нашими панелями, (б) Cordis-плагины, где наши соседствуют с нативными. Наружу торчит только один канал — вызовы к внешним провайдерам моделей через API-ключи.

## 2. Новые продуктовые требования (зафиксированы в этом заходе)

### 2.1 Управление ключами и моделями
- UI-панель массового добавления API-ключей по вендорам (не по одному, а списком/CSV-вставкой — прямой ответ на «удобный способ добавить кучу ключей»), расширяющая существующий credential-механизм плагина `llm`, а не отдельное хранилище.
- Реестр моделей: `model_id`, вендор, `historical_score` (см. п.7/12 в `mas_audit_answers.md` — обязательно с версией/fingerprint и датой оценки, иначе дрейф моделей вендоров невозможно будет отследить постфактум).
- Лимиты бюджета/rate-limit на ключ — параметры для `circuit_breaker.py` (порог отказов, recovery timeout) настраиваются здесь же, а не зашиты в код.

### 2.2 Настройка ролей — вручную или автоматически
- Пользователь может **вручную закрепить** роль за конкретной моделью — такие пары исключаются из аукциона (`role_auction.py` их не трогает).
- Оставшиеся роли уходят в автоматическое назначение (аукцион + peer review, см. `role_auction.py`, обоснование — симуляция в `mas_deepened_analysis.md`, п.8/18).
- Пользователь может задать **набор ролей** для конкретной задачи (не только «кто», но и «какие роли вообще существуют в этом прогоне» — например, для маленькой задачи не нужен отдельный security-критик).

### 2.3 Таблица утверждения назначения ролей (ваша правка)
После работы `assign_role()` рендерится таблица:

| Роль | Модель | Историч. скор | Скор рецензии | Обоснование рецензента (кратко) |
|---|---|---|---|---|

Кнопки на строку: **утвердить** / **назначить вручную** / **перезапустить аукцион для этой роли**. Это **блокирующий чекпойнт** — оркестратор не переходит к планированию, пока таблица не утверждена целиком. Реализуется как отдельная Cordis-панель, подписанная на событие `role_assignment_proposed` в event log (`event_log.py`) и публикующая `role_assignment_confirmed` по нажатию.

### 2.4 Второй такой же чекпойнт — утверждение плана
После планировщика — аналогичный блокирующий экран с самим планом (не таблица, а редактируемый текст/структура) и кнопками «утвердить» / «отправить на доработку с комментарием». Обоснование то же, что и для ролей: дешевле поправить до старта исполнения, чем после (MAST — специфика задачи, раздел 1 `mas_audit_answers.md`).

### 2.5 Уровень детализации по умолчанию
Общий чат виден полностью и всегда; точечные мини-споры — свёрнуты в карточку с раскрытием по клику (паттерн уже принят в экосистеме Harness, `dsh-ui-concise`). Никаких дополнительных обязательных подтверждений на каждый мини-спор — это свело бы на нет весь эффект confidence-gated дебатов (расчёт в `mas_deepened_analysis.md`, п.19/23: без гейтинга задача может стоить $270–975).

## 3. Фазы разработки

Каждая фаза заканчивается не «полным тестированием», а маленьким целевым дымовым прогоном (в духе п.54) — соответствует ограничению бюджета: тратим реальные деньги на API только тогда, когда именно эта фаза даёт что-то новое проверить.

### Фаза 0 — Каркас и первый дымовой прогон
**Цель:** доказать, что путь «задача → один вызов модели → критик → результат» вообще проходит через Harness, прежде чем усложнять.
**Строим:** `harness_adapter.py` как реальный Cordis-плагин (anti-corruption layer поверх `ctx.llm`); `event_log.py` как реальный session-плагин; один агент без команды, без дебатов.
**UI:** минимальный — используем существующий чат Harness как есть, без кастомных панелей.
**Экономика:** буквально один дешёвый вызов одной модели.
**Критерий выхода:** одна реальная задача проходит от ввода до результата без падений.

### Фаза 1 — Ключи, модели, реестр
**Цель:** UI из п.2.1.
**Строим:** панель массового добавления ключей (расширяет `llm`-плагин); реестр моделей с метаданными; интеграция лимитов с `circuit_breaker.py`.
**Критерий выхода:** добавлены 3+ вендора, зарегистрировано 5+ моделей, лимиты видны и редактируемы в UI.

### Фаза 2 — Оркестратор и назначение ролей
**Цель:** реальный `role_auction.py` с настоящим независимым peer-review вызовом (не заглушкой), плюс UI из п.2.2–2.3.
**Строим:** Cordis-плагин «оркестратор»; панель ручной блокировки ролей; таблицу утверждения; `tie_break.py` для равных скоров.
**Критерий выхода:** реальный прогон с 3–4 живыми моделями даёт осмысленную таблицу, пользователь её утверждает, зафиксированные вручную пары не переигрываются аукционом.

### Фаза 3 — Планировщик и утверждение плана
**Цель:** роль «планировщик» + UI из п.2.4.
**Строим:** промпт/логику планировщика; экран утверждения плана с возможностью отправить на доработку.
**Критерий выхода:** реальная задача → роли утверждены → план сгенерирован → пользователь утверждает или отправляет на доработку с комментарием, и план меняется по существу комментария.

### Фаза 4 — Командное исполнение: общий чат + точечные споры
**Цель:** многоагентное исполнение с DOWN-гейтингом (п.19 `mas_audit_answers.md`) и точечными мини-спорами (п.21 — простое пороговое скорирование релевантности, без переусложнения эвристиками для NP-hard случая, который здесь не нужен — см. уточнение в `mas_deepened_analysis.md`).
**Строим:** триггер спора по confidence score; фильтр релевантности участников по аналогии с candidate function из AutoGen; UI — свёрнутые карточки споров (п.2.5) с разворотом.
**Критерий выхода:** реальная задача вызывает минимум один гейтированный спор среди релевантного подмножества, спор корректно сворачивается по критерию стабилизации, UI отображает это как ожидается.

### Фаза 5 — Критик и верификация
**Цель:** многоуровневая верификация (не только финал), `evidence_requirement.py` как фильтр допустимости аргументов в спорах, security-чек-лист.
**Строим:** промежуточные проверки на каждом хэндовере; интеграция evidence-фильтра в UI спора (аргументы без отсылки визуально помечены как недопустимые).
**Критерий выхода:** критик ловит намеренно внесённую в тестовом прогоне ошибку формата/логики на промежуточном, а не только финальном шаге.

### Фаза 6 — Устойчивость и безопасность
**Цель:** `circuit_breaker.py` подключён ко всем вызовам моделей без исключения; `sandbox_permissions.py` — пересечение прав для субагентов; маркировка происхождения сообщений между агентами (защита от косвенной инъекции, п.38).
**Критерий выхода:** симуляция отказа вендора посреди задачи → graceful degradation, а не падение; симуляция инструкции, встроенной в вывод одного агента для другого → она помечена как данные, а не выполняется как команда.

### Фаза 7 — Диверсити-монитор и полировка UX
**Цель:** `diversity_monitor.py` как опциональный индикатор «здоровья команды» в UI (не блокирующий, справочный); бюджетная панель, расширяющая существующий `dsh-usage-chart`-паттерн нашей раскладкой по агентам/ролям; финальная визуальная полировка под родной стиль Harness.

## 4. Технологический стек

- Бэкенд — TypeScript/JS-плагины под Cordis (тот же язык, что и нативные плагины Harness — не изобретаем собственный рантайм).
- Взаимодействие со всей остальной кодовой базой — только через `HarnessGateway` (`harness_adapter.py`/аналог на TS) — единая точка адаптации под breaking changes dev-preview версий.
- Хранение состояния — append-only event log (`event_log.py`) поверх файловой системы `~/.dsh`, без внешней БД — соответствует локальной, «песочничной» модели Harness и бюджетным ограничениям (нет инфраструктуры для поддержки).
- UI-панели — тем же стеком, что и нативный Web UI Harness (см. прецеденты `dsh-dashboard`, `dsh-usage-chart`) — конкретный фреймворк подтверждается на Фазе 0 по факту изучения реальной, а не документированной публично структуры плагина UI.

## 5. Что сознательно откладывается, а не забыто

- Точная формула весов в `score_role_fit` (сейчас 0.5/0.5, см. `role_auction.py`) — калибруется на калибровочном наборе задач начиная с Фазы 2, не раньше (нет смысла калибровать до того, как есть реальные данные).
- Полноценная OpenTelemetry-инструментация (п.46) — полезна, но не блокирует MVP; добавляется на Фазе 6 вместе с остальным хардненингом.
- Конкретный движок для панелей Web UI Harness — заявленный в п.4 стек подтверждается фактом на Фазе 0, а не сейчас, потому что все найденные подтверждения (`dsh-dashboard`, `dsh-usage-chart`) — это сторонние сообщения о релизах, а не официальная документация API плагинного UI, которую мы пока не видели напрямую.

## 6. Первый спринт — конкретный и маленький

Ровно Фаза 0. Ничего из UI, ключей, ролей, дебатов — только: `harness_adapter.py` как реальный плагин, `event_log.py` как реальный session-плагин, один агент, один вызов, один критик-чек, один реальный дешёвый прогон до результата. Это первая точка, где вообще тратятся деньги на живой API — и именно поэтому она должна оставаться маленькой.
